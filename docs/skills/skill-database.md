# Skill: skill-database

## Purpose
Design and apply safe relational-database migration changes.

**Applicability**: This skill's examples use PostgreSQL + Flyway as a concrete reference. The safety matrix, backfill strategy, and rollback guidance generalize to any SQL database + migration tool (Liquibase, Drizzle, Prisma Migrate, Alembic, ActiveRecord, Django, etc.). Translate path and filename conventions to your stack.

**Scope tag**: `stack:backend-*` with a persistence layer. Frontend / mobile stacks that don't own schema should not invoke this skill.

## Reads
- `docs/conventions/backend-conventions-general.md` (when stack is backend)
- Any stack-specific database convention file under `docs/conventions/` (e.g., `backend-conventions-database.md`)
- `docs/conventions/backend-conventions-testing-style.md` (when stack is backend)
- current migrations and task context

## Writes
- Migration files under `{project_root}` in the stack's migration location:
  - Flyway (Java/Spring): `src/main/resources/db/migration/V{timestamp}__*.sql`
  - Liquibase: `src/main/resources/db/changelog/*.xml` or `.yaml`
  - Drizzle / Prisma / Knex (Node): `drizzle/` or `prisma/migrations/` or `migrations/`
  - Alembic (Python): `alembic/versions/`
  - ActiveRecord (Rails): `db/migrate/`
- Migration decisions in `docs/agent/runs/{story_id}/decision-log.md`

## Naming Convention
```
V{YYYYMMDDHHMM}__{description}.sql
```
Examples:
- `V202603061200__create_warehouse_table.sql`
- `V202603061215__add_status_column_to_order.sql`

## Migration Safety Matrix

| Change Type | Safe? | Requires |
|-------------|-------|----------|
| CREATE TABLE | ✅ Yes | — |
| ADD COLUMN (nullable) | ✅ Yes | — |
| ADD COLUMN (NOT NULL + default) | ✅ Yes | Default value |
| ADD COLUMN (NOT NULL, no default) | ❌ No | Backfill first |
| DROP COLUMN | ❌ No | Explicit approval + deprecation period |
| RENAME COLUMN | ❌ No | Explicit approval + app code change |
| ALTER COLUMN TYPE (widening) | ⚠️ Caution | Test data compatibility |
| ALTER COLUMN TYPE (narrowing) | ❌ No | Data migration plan |
| DROP TABLE | ❌ No | Explicit approval + backup |
| CREATE INDEX | ✅ Yes | Consider CONCURRENTLY for large tables |
| DROP INDEX | ⚠️ Caution | Verify no query relies on it |
| ADD CONSTRAINT (FK) | ⚠️ Caution | Ensure data integrity first |
| ADD CONSTRAINT (CHECK) | ⚠️ Caution | Validate existing data |

## Schema Conventions
These are defaults; override only when the project already sets its own and you see them in existing migrations.

- Audit columns on all non-lookup tables:
  - `date_created TIMESTAMP DEFAULT now()`
  - `user_created VARCHAR(50)`
  - `date_changed TIMESTAMP DEFAULT now()`
  - `user_changed VARCHAR(50)`
- Primary key: auto-increment bigint (`BIGSERIAL` in Postgres, `BIGINT AUTO_INCREMENT` in MySQL, `BIGINT GENERATED BY DEFAULT AS IDENTITY` in SQL standard)
- Foreign key naming: `fk_{table}_{referenced_table}`
- Unique constraint naming: `uk_{table}_{column}`
- Index naming: `idx_{table}_{column}`
- Schema name: match the existing project convention; if greenfield, record the chosen name in `decision-log.md`.

## Backfill Strategy
When adding NOT NULL column to existing table:
1. Add column as nullable.
2. Create backfill migration with UPDATE statement.
3. Add NOT NULL constraint in subsequent migration.
4. Document in decision log.

## Rollback Considerations
- Most migration tools are forward-only by default (Flyway, Alembic's `autogenerate`, Drizzle).
- For critical changes, create a separate "undo" migration script (not auto-executed).
- Document rollback steps in decision log for destructive changes.

## Guardrails
- Forward-only migrations.
- Explicit PK/FK/index strategy.
- No destructive changes without explicit approval in decision log.
- Test migrations against production-like data volume.
- Use `CREATE INDEX CONCURRENTLY` for large tables in production.
